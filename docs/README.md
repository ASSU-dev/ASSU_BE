# docs

팀이 함께 보는 설계·운영 문서를 둔다. 코드만 읽어서는 알 수 없는 **왜**를 남기는 곳이다.

> 공개 저장소다. IP·인스턴스 ID·DB 주소/계정·토큰·키 경로는 쓰지 않는다. 각자 로컬 `~/.assu/infra.env`에 두고 변수 이름으로만 참조한다.

## 구조

| 폴더 | 내용 | 파일명 |
|---|---|---|
| `guide/` | 개발·운영하면서 반복해서 찾아보는 안내서 | `주제.md` |
| `adr/` | 되돌리기 어려운 설계 결정과 이후 작업자가 지켜야 할 규칙 | `NNNN-제목.md` (번호는 1씩 증가) |

새 폴더는 같은 종류의 문서가 2개 이상 생길 때 만든다.

## 가이드 작성 규칙
- 제목 바로 아래에 최종 수정일과 수정자를 적는다. 문서를 고칠 때마다 갱신한다.
  ```markdown
  > 최종 수정: YYYY-MM-DD · 수정자: GitHub ID
  ```
- 문서 맨 아래 `## 변경 이력` 표에 한 줄을 추가한다. 최신 항목이 위로 오게 한다.
  ```markdown
  | 날짜 | 수정자 | 내용 |
  |---|---|---|
  | YYYY-MM-DD | GitHub ID | 무엇을 왜 바꿨는지 한 줄 (#이슈) |
  ```
- 내용이 바뀐 구조와 맞지 않게 되면 문서를 지우지 말고 고친다. 지난 구성은 이력에 한 줄로 남긴다.

## ADR (Architecture Decision Record)

### 언제 쓰나
- 다른 개발자가 모르고 되돌리면 문제가 생기는 결정
  - 예: 연관관계 로딩 전략, 인증 흐름, 배포 구조
- 여러 대안을 비교해 하나를 고른 결정

### 작성 규칙
- 결정이 바뀌면 기존 문서를 고치지 않는다.
  - 새 ADR을 쓴다.
  - 기존 문서의 상태를 `대체됨 (ADR-NNNN)`으로 바꾼다.
- 관련 이슈·PR 번호를 적는다.
- 수치는 측정 방법과 함께 적는다.

### 템플릿
```markdown
# ADR-NNNN: 결정 한 문장

- 상태: 제안 | 채택 (YYYY-MM-DD) | 대체됨 (ADR-NNNN)
- 관련: #이슈, #PR

## 맥락
무엇이 문제였고 어떤 제약이 있었나

## 결정
무엇을 하기로 했나. 검토한 대안과 기각 이유

## 결과
얻은 것과 감수한 것

## 이후 작업 시 주의사항
이 결정 때문에 지켜야 할 규칙
```
