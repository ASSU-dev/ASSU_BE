# ADR-0002: 앱 CPU limit은 노드 크기(2코어)로 두고, 같은 노드 안의 HPA는 보류한다

- 상태: 채택 (2026-11-04)
- 관련: #545, #569, manifest#17·#22·#24·#25

## 맥락
- 환경(prod/dev)마다 앱이 뜨는 노드는 t3.medium(2 vCPU) 1대이고, 앱은 `nodeSelector`로 그 노드에 고정된다.
- HPA(최대 2대, CPU 400m 기준)를 dev에서 검증했다. 확장·축소 동작은 정상이었다.
- 같은 부하(초당 5→120건, 24분)를 세 조건으로 비교했다.

| 조건 | 120 rps 구간 p95 | 콜드 스타트 | 오류 |
|---|---|---|---|
| limit 1코어 + HPA 2대 | 8.8~11.9초 | 회복 못 함 | 0 |
| limit 2코어 + HPA 2대 | 0.8~7.2초 | 약 4분 | 39 (Traefik 재시작) |
| limit 2코어, 1대 | 1.2~1.6초 | 1분 | 0 |

- 같은 노드 안에서 파드를 늘리면 새 파드의 기동(85초간 1코어)과 JIT 컴파일이 기존 파드의 CPU를 뺏는다. limit 1코어에서는 JVM이 SerialGC를 고르고 JIT 컴파일 스레드 2개가 요청 스레드와 한 코어를 나눠 써서 콜드 파드가 4~8분 느렸다.

## 결정
- 앱 컨테이너 `limits.cpu`를 노드 크기인 2000m으로 둔다. requests는 200m을 유지한다.
- ResourceQuota `limits.cpu`는 롤링 배포의 surge 1대를 포함해 6으로 둔다.
- 같은 노드 안에서 동작하는 HPA는 도입하지 않는다. 두 번째 노드가 생기면 다시 검토한다.
- 앱이 노드 CPU를 독점할 수 있으므로 같은 노드의 Traefik 등 이웃 파드에 `requests`를 보장한다(Traefik 100m/64Mi).
- 기동 후 워밍업 코드(self-call)는 만들지 않는다. 2코어를 혼자 쓰면 워밍업이 1분 안에 끝난다.

### 검토한 대안

| 대안 | 기각 이유 |
|---|---|
| HPA 유지(가용성 목적) | 부하 시 확장이 오히려 해롭다. 파드 1대 재시작(약 85초)은 현재 트래픽에서 수용한다 |
| 2대 고정(warm standby) | 메모리 2Gi, RDS 커넥션 최대 20개. 트래픽이 노드 상한에 가까워지면 재검토 |
| 워밍업 후 Ready | 코드 변경과 기동 시간 증가. 실험에서 불필요함이 확인됐다 |
| limit 제거(requests만) | 이웃 파드 보호를 requests에만 의존하게 된다 |

## 결과
- 같은 노드로 초당 약 120건을 p95 1.5초 안에 처리한다(이전 한계 초당 20~25건).
- 처리량의 상한은 노드다. 초당 100건 근처가 상시 보이면 노드 상향이나 두 번째 노드를 검토한다.

## 이후 작업 시 주의사항
- 앱 limit을 올리거나 새 워크로드를 같은 노드에 둘 때 Traefik·Alloy·RabbitMQ의 requests를 함께 본다. requests가 없는 파드는 노드가 포화될 때 먼저 죽는다.
- dev에서 부하를 측정할 때는 HikariCP 풀(2개)이 상한이 될 수 있다. 측정 기간에만 올린다.
- `externalTrafficPolicy: Local`은 로컬 Traefik이 살아 있을 때만 노드를 격리한다. 로컬 Traefik이 죽으면 ServiceLB가 다른 노드 Traefik으로 넘긴다.
